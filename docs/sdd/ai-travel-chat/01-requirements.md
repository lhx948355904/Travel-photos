# AI 游玩与摄影交流页：具体功能需求

状态：需求草案；产品方向已按用户答复更新，尚待确定实时证据标准、外部数据提供方与调用额度，见 [05-决策记录](05-decisions.md)。本文描述目标行为，不表示仓库已有 AI 接口。

## 1. 目标与现状依据

目标是在现有旅行摄影地图之外提供一个独立的自然语言交流页面。用户询问景色、游玩或摄影，系统逐步显示回答；涉及可核实的地点时，回答、按序排列的地点列表、地图点位和相关照片相互对应。超出主题时，友好告知服务范围。

已核对的现状：

| 位置 | 已有行为 | 对本需求的约束 |
| --- | --- | --- |
| `frontend/src/App.tsx`、`pages/Home/index.tsx` | 有首页和 `/map` 路由，首页有进入地图入口 | 交流页及入口均需另行设计；现有路由没有 AI 页面 |
| `pages/Map/index.tsx`、`components/MapView/MapView.tsx` | 地图展示相册地点，点击照片点进入画廊；搜索可定位高德 POI | 推荐结果点须与相册点区分；不能让推荐点误触发管理员添加地点 |
| `components/MapView/SearchBox.tsx` | 高德输入提示和地点搜索，选择后得到名称及坐标 | 这是用户主动搜索能力，并非 AI 推荐、批量坐标核实或景点照片接口 |
| `api/location.ts`、`types/index.ts` | 地点列表含 ID、名称、坐标、封面、照片数；详情含描述、照片 | 现有相册可供关联照片，但列表没有推荐理由或当前季节信息 |
| `backend/.../LocationController.java`、`LocationService.java` | 提供公开读取地点及详情；只返回站点拥有者且有可用照片的地点 | 不能把数据库里的所有 POI 或全网照片视作现成数据 |
| `backend/.../WebSecurityConfig.java` | 地点 GET 放行，写入需鉴权 | 用户已确认访客和管理员都可使用 AI 页；新接口仍需单独落实服务端权限与限流 |
| `.env.example`、`AI_PRODUCT_ROADMAP.md` | 有 AI 配置样例和规划文字 | 在前后端实际源码中未找到可调用的 AI 问答、流式响应或推荐接口 |

## 2. 用户场景与功能点

### FR-01 独立交流页

- 提供独立页面，不把对话输入替换为 `/map` 现有的地点搜索框。页面包括问题输入、对话区、结果列表和地图区域；小屏也能查看完整内容。
- 访客和管理员都可使用交流页，首页和地图页都提供入口；独立页的具体路由地址在技术设计时确定。服务端应允许未登录访问本功能，同时对公开调用设置限制。
- 对话仅在当前页面会话中保留，不跨次保存；重新打开页面不恢复此前聊天记录，也不新增对话历史表。
- 初次打开给出主题提示及示例问题，例如“适合拍秋景的地点有哪些？”“如何拍逆光风景？”

### FR-02 输入和流式反馈

- 提交文字问题后，显示请求中、持续生成、完成或失败状态。生成中的文本增量显示；用户能停止当前回答并再次提问。
- 同一次提交只形成一轮回答；新问题到来时，旧请求的迟到内容不能覆盖当前列表或地图。
- 流式文本与结构化地点结果分开处理：只有完整且经过服务端校验的地点结果才能上图，不能从尚未完成的自然语言段落中猜坐标。

### FR-03 主题识别与委婉回绝

- 允许景色、观景、游玩、目的地选择、旅行摄影、拍摄技巧及这些主题的合理追问。
- 纯粹无关的问题返回简短、礼貌的范围说明，并引导用户改问景色、游玩或摄影；不生成地点列表和地图点。
- 混合问题只处理主题内的部分，明确告知其余部分不属于本页服务范围。不能仅靠前端隐藏输入来完成范围判定；服务端也应约束模型输出。

### FR-04 景色与地点回答

- 对可关联到具体地点的问题，回答包含地点名称、推荐理由和依据类型，并提供可点选的地点结果。
- 地点名称存在同名或歧义时，结合城市/地区确认。经纬度必须来自已确认的相册地点或可靠的地点检索结果，不能由模型凭空填写。
- 无法核实坐标时，可给文字解释，但明确标为“位置待确认”，不在地图上创建点位。
- 推荐可包含未收录在本站相册的外部景点；可展示有授权的外部照片。界面应标明“相册地点/外部地点”“本站照片/外部授权照片/暂无照片”。外部地点和照片的具体提供方、授权与字段契约仍待确认。

### FR-05 地图与列表联动

- 列表每项与地图点具有同一个稳定结果 ID。点击列表使地图聚焦相应点；点击点突出对应列表项和照片、理由。
- 结果列表展示排名、地点名称、地区、推荐理由、照片或无图状态。地图显示本轮可定位的结果，并调整视野覆盖可用点。
- 推荐结果点与 `/map` 现有的相册照片 Marker 语义不同；显示推荐结果不能创建相册地点，也不能改变原有上传/删除流程。
- 无可定位结果时，地图保持空结果提示，回答仍可展示。

### FR-06 时间与季节推荐

- 用户提出“现在/这个周末/秋景”等问题时，明确使用的日期、地区、实时数据发布时间和依据。如果没有地区，先请用户补充目的地或出发城市；补充前不输出具体地点排名，不默认推断用户位置。若只给出出发城市，再追问愿意去多远，得到回答后才确定搜索范围。
- 模型可参与理解问题、解释理由与排序，但候选地点、坐标和照片必须来自明确的数据源。排序只使用可说明的依据；每个结果给出与时间/季节的关联理由。
- “当前适合”类地点推荐必须取得符合最终证据标准的实时数据后才输出；实时源未接入、过期或查询失败时不输出此类地点排名，可提示重试或改问一般景色/摄影知识。实时天气只能证明天气，不能单独证明花期、红叶或景区当日开放；所需信号和新鲜度仍需确定。
- 季节不是固定等于秋季；“当前”按实际日期和所选地区解释。旅行日期和照片拍摄日期是历史记录，不能证明当前景况。

### FR-07 照片展示

- 使用本站相册照片时，以现有地点详情为关联依据；照片卡可进入现有画廊或明确的详情视图。
- 允许有授权的外部照片；展示前需明确提供方、许可、署名和可用性。找不到合法可展示的照片时显示占位及来源说明，不能用 AI 生成图冒充现场照片。
- 图片加载失败不影响文字回答、列表和地图定位。

### FR-08 失败与质量边界

- 模型超时、流中断、地图或照片加载失败、地点无匹配、季节证据不足时分别给出可理解的提示；允许重试，不把未完成的推荐展示为已验证结果。
- 对结果中的地点、坐标、照片引用、数量、文本长度做服务端校验；前端只渲染可信字段并避免把模型文本当 HTML 执行。

## 3. 拟影响的代码与数据范围

这是实现阶段的影响分析，不是本次改码清单：前端会涉及路由、首页和地图页入口、独立页面、流式请求封装、地点列表和地图组件；后端需新增受控的 DashScope 问答服务及流式接口，并复用地点/照片读取能力。现有 `LocationVO` 缺少描述和照片明细，需按地点取详情或设计专用只读结果。外部景点、有授权的外部照片和实时数据都要定义提供方、授权、字段、缓存及失效规则；这些均不在现有接口中。当前无需对话历史表。

预期数据流：问题及上下文 → 服务端主题判断和数据检索 → 模型生成文字/理由 → 服务端核验结构化地点及照片引用 → 前端持续显示文字 → 一次性提交可展示的排名列表与地图点。

接口路径、请求方式、流协议、具体 DashScope 模型和调用额度都不在本文中当作既定事实；“访客可用”与“不跨次保存”的产品规则已确认，但后端实现方式尚未设计。[外部与实时数据调研](06-source-research.md) 列出候选来源，并未选定最终接口。
