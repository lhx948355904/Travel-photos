# 台球比分记录 · SDD 规格

## 目标与范围

在现有站点增加 `/scores` 公开页面。游客可浏览比赛；现有管理员登录后可创建、编辑、删除比分，并可为单场比赛上传一张记分图片。初版还提供搜索和按月份筛选，并复用 `frontend/DESIGN.md` 的暗色配色；2026-10-25 的界面迭代已按用户要求移除筛选栏并改为浅色，以下迭代规格优先。

## 数据与接口

- `score_record`：标题、双方姓名、双方局数、比赛时间、可选场地和备注、可选图片对象 Key、创建/更新时间、软删除标记。
- `GET /api/scores`：公开分页查询，支持关键词与 `YYYY-MM` 月份筛选，按比赛时间倒序。
- `POST/PUT/DELETE /api/admin/scores`：仅 `ROLE_ADMIN`，验证必填项、局数范围、图片归属。
- `POST /api/admin/scores/image`：仅管理员，复用现有图片校验和 COS/本地存储。无图时返回 `imageUrl: null`，前端不生成图片容器。

## 验收条件

1. 未登录能看列表、筛选和图片；创建、修改、删除、上传均返回 401，管理员可以完成操作。
2. 新增与修改后列表显示最新比分；删除后记录不再公开；无数据时有明确空状态。
3. 无图片的比赛没有图片元素；有图片时可打开预览；编辑时可以替换或移除图片。
4. 局数为 0–99 的整数且两者不能同时为 0；标题、选手、时间必填；图片不超过 10 MB。
5. 桌面与手机可用，键盘可达；执行前后端项目现有构建与关键测试。

## 边界

沿用站点现有单管理员 JWT 机制，不增加新的用户注册或角色管理。图片上传与比分保存为两次请求，若上传后未保存比分，可能留下未引用对象；后续可做定时清理。

## 验证记录

- 后端 `ScoreRecordRouteTest` 4 项通过：游客只读、管理员增删改、筛选与软删除、比分校验、图片上传和移除。
- 前端 `npm run build`、`npm run lint`、`npm test` 通过。
- 初版浏览器视觉检查当时未完成；后续界面迭代已在浏览器中复核桌面和手机布局。

## 2026-10-25 界面迭代规格

### 目标

1. 移除首页首屏原文案和台球桌插画，改为真实斯诺克选手照片轮播。手动切换、自动轮播、暂停和低动态效果都可用；图片来源、许可可追溯。
2. 比赛记录移除关键词/月筛选栏，保留按比赛时间倒序与分页。
3. 管理员可选填每局双方得分。整场比分等于逐局胜局数；无逐局数据的历史记录仍可编辑和浏览，不生成虚构图表。
4. 有逐局数据时展示分局对比和个人得分曲线；曲线仅用于观察得分波动，不推断技术水平或胜率。
5. 页面改为浅色系，沿用 DESIGN.md 的字体分工、宽松布局与圆角尺度；浅色要求优先于 DESIGN.md 的暗色背景建议。

### 数据与边界

- 新表 `score_frame`：比赛 ID、局序、双方得分。每局得分为 0–200 的整数且不得相同；最多 35 局。
- 上传/保存时如有逐局得分，后端核算双方胜局总数必须等于整场比分。编辑时可清空逐局数据，图表随之消失。
- 图表展示实际逐局得分；所谓“稳定性参考”使用相邻局得分变化的平均绝对值，越低代表得分波动越小，不代表实际竞技能力评价。
- 海报使用 Wikimedia Commons 可复用照片，页面提供摄影者与许可链接。海报人物与本站比赛数据没有关联。

### 验收

- 桌面与移动端可操作轮播，自动切换在悬停/聚焦与低动态偏好时停用；图像失败时仍可读。
- 筛选栏不再显示；记录、分页、管理员操作继续可用。
- 逐局输入的总局数不匹配时拒绝保存；更新后图表与记录同步；历史记录无图表时有说明。
- 构建、lint、现有测试及逐局数据接口测试通过。

### 验证记录

- `npm run build`、`npm run lint`、`npm test` 均通过；前端共 24 项测试通过。
- `ScoreRecordRouteTest` 共 5 项通过，包含逐局得分与整场局数一致性、平局拒绝、更新清空逐局数据。
- 浏览器以本地后端核对真实空状态、海报手动切换、照片署名；以临时示例数据核对桌面和 390px 手机端的七局柱形图、完整趋势曲线与横向滚动。示例数据已清理。
- 逐局图表需要管理员录入真实逐局得分；旧记录仍可显示整场比分，未补录前不会显示图表。

## 2026-10-26 比赛记录与图库迭代

### 目标与边界

- 单页最多 6 场比赛叠放，默认最新比赛在上；悬停、点击或键盘聚焦可展开任意一场。卡片标签和下方切换按钮可拖动排序，顺序保存在当前浏览器的 `localStorage`，不改变比赛时间和其他访客的顺序。
- 每场比赛最多 20 张 JPG、PNG 或 WebP 图片，单张不超过 10 MB。上传沿用管理员图片接口，保存比赛时提交图片 Key 列表；编辑时可单张移除。
- 新增 `score_image` 关联表，迁移时把旧 `score_record.image_key` 回填为第一张图片。旧请求的 `imageKey` 和响应中的 `imageKey/imageUrl` 继续兼容。
- 图库汇总所有比赛图片，按图片 Key 生成稳定的错落布局。点击后根据图片实际宽高选择横图上下、竖图左右的信息布局；窄屏统一上下布局。

### 验收条件

1. 多场记录不再逐条向下排列；展开和排序可操作，刷新后本机顺序保留。
2. 多图上传、返回顺序、移除单图和旧单图兼容均可用；无图记录不生成图片元素。
3. 图库图片打开后能看到比赛时间、标题、比分、结果及可选场地和备注；图片保持完整比例。
4. 移动端、键盘操作和低动态偏好可用；前后端构建与关键测试通过。

### 2026-10-26 交互修订

- 比赛卡片改为横向排列，卡片间只保留少量遮盖。卡片默认收起；点击卡片或标题按钮才展开，再次点击收起，悬停不改变展开状态。横向滚动浏览当前页更多比赛，标题仍可拖动排序。
- “比赛图库”始终位于比赛记录之后，并在记录标题区提供直达按钮。展开有照片的比赛后，可跳转并只看本场照片，再切换回全部照片。无照片时显示上传指引。
- 兼容尚未部署多图接口的旧服务：响应只有 `imageKey/imageUrl` 时，图库仍显示旧照片。若管理员选择了多张而旧服务只保存第一张，保存后明确提示；完整多图持久化需要部署后端迁移和新版服务。

### 多图只保存第一张的修复

- 原因：开发页的 `/api` 代理至线上旧版服务。旧版接口忽略 `imageKeys` 列表，只保存兼容字段 `imageKey` 中的第一张；上传成功只是对象存储写入成功，不等于比赛记录已经关联全部图片。
- 新版公开接口 `GET /api/scores/capabilities` 返回 `maxImagesPerRecord: 20`。管理员界面先检查该能力；旧服务返回 404 时，只允许每场选一张，并保留替换功能，避免继续产生未关联的第二张照片。
- 新版服务通过 `score_image` 表保存全部图片 Key。接口测试在创建后重新查询比赛，确认两张图片均已持久返回。发布脚本检查 Flyway V6 和能力接口，防止只更新前端而遗漏后端或迁移。
- 部署新版服务后，旧版时期未关联的第二张图片不会自动知道属于哪场比赛，需要管理员重新补传或提供图片 Key 后人工核对关联。
